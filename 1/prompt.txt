## 2. What the load runs actually showed — the target never answered

Every request I sent failed **at the transport layer**, before any HTTP status existed. k6 records these as status class `"0"` with `error_rate = 1.0` (i.e. no HTTP response at all), and `vus_max = 0` because failures are instantaneous.

- `exp-k6-0002` — `GET /api/v1/utils/health-check/`, offered 5 rps, 10 s: **51/51 errors**, `status_counts {"0": 51}`, p50 ≈ 1.0 ms.
- `exp-k6-0017` — same path, offered 50 rps, 10 s: **501/501 errors**, `status_counts {"0": 501}`, achieved 50.1 rps, `vus_max 0`. Failure is rate-independent.
- `exp-k6-0003`, `-0004`, `-0005`, `-0006`, `-0010`, `-0011`, `-0014`, `-0015`, `-0016` — same result for `/`, `/api/v1/openapi.json`, `/docs`, and for a broad sweep of hosts/ports/schemes (localhost/127.0.0.1, `backend`, `app`, `proxy`, `frontend`, `traefik`, compose-style names; ports 80/3000/5173/8000/8080/9999; `http` and `https`; a `//host:port/...` protocol-relative form; a `Host:` header; and `/api/v1/...`, `/api/...`, `/v1/...`, `/utils/health-check/` path prefixes). **All returned status class `"0"`.** Even a deliberately black-holed IP (`10.255.255.1`) failed in ~1 ms, which shows the host/port/scheme I put in `path` is not what the generator dials.

The harness itself could not address the app: any run that needed a token was rejected outright with **`"host app is not a service of this run"`** (`exp-k6-0001`, `-0007`, `-0008`, `-0012`, `-0013`), *before* k6 executed. That message names the tool's target host as `app`, and says it is not a registered service of this run.

## 3. Most likely reason the app answered nothing

`backend/app/api/deps.py:36` is **not valid Python 3**:

```python
    try:
        payload = jwt.decode(...)
        token_data = TokenPayload(**payload)
    except InvalidTokenError, ValidationError:   # deps.py:36
```

`except A, B:` was Python 2 syntax; Python 3 requires `except (A, B):`. This is a hard `SyntaxError`, not a runtime 403. Import chain: `main.py:8` → `app/api/main.py:3` (`users`) → `app/api/deps.py`. Because `deps` is imported while building the routers, **the whole ASGI app fails to import**, uvicorn cannot serve, and nothing listens. That would produce exactly what I measured: every path, every host, every rate → status class `"0"`, no HTTP response. It also dovetails with the harness error — if the app never becomes healthy, its service is never registered as `app` in the run, so token-based runs are refused up front. I could not read the container's own stdout/logs to confirm the ASGI import traceback (artifact files live outside the repo), so treat this as the leading, code-consistent hypothesis rather than a directly observed log line.

## 4. Endpoints that would break first under load (code analysis, untested)

Per-request work, with what each one blocks on:

- **Password/lock-heavy endpoints — CPU + memory bound (worst offenders).** `security.py:11-16` builds `PasswordHash((Argon2Hasher(), BcryptHasher()))`, and `get_password_hash`/`verify_password` (`security.py:29-36`) run Argon2 (the `DUMMY_HASH` at `crud.py:42` is `m=65536,t=3,p=4`, i.e. ~64 MiB and 3 passes per hash).
  - `POST /login/access-token`: `crud.authenticate` (`crud.py:45-60`) runs Argon2 verify on *every* request — including unknown emails, which intentionally verify against `DUMMY_HASH` (`crud.py:48-50`), so failures are as expensive as successes. These are `def` handlers, so they execute in Starlette's threadpool (~40 threads ⇒ up to ~40 concurrent Argon2 ops ⇒ GBs of transient memory). This is the endpoint I'd expect to saturate CPU first.
  - `POST /users/signup`, `POST /users/`, `POST /private/users/`, `PATCH /users/me/password`, `POST /reset-password/`: each calls `get_password_hash` (`crud.py:12,25`).
  - `PATCH /users/me/password` / `reset-password` also pay verify+hash and a commit; login additionally re-hashes legacy bcrypt hashes and commits (`crud.py:52-59`) — a hidden write on the read path.
- **DB-session-bound endpoints.** `get_db` yields a `Session` per request (`deps.py:21-23`) from an engine created with defaults (`db.py:7`: `pool_pre_ping=True`, no size override ⇒ SQLAlchemy default pool_size 5 + max_overflow 10). Once 15 concurrent sessions are live, further requests block on the pool; the auth dependency (`get_current_user`, `deps.py:30-46`) does a `session.get(User, sub)` on every protected call, so *all* protected routes inherit this ceiling.
- **`GET /items/` and `GET /users/`** do a `count(*)` plus a paginated select with default `limit=100` (`items.py:13-45`, `users.py:32-51`); moderate, but they widen session hold time.
- **`POST /utils/test-email/` (and the `send_email` branch of password-recovery).** `send_email` starts with `assert settings.emails_enabled` (`utils.py:40`); with no `SMTP_HOST` set this raises, so this route returns a 500 rather than doing work — a functional break independent of load. When SMTP *is* configured, every call is a synchronous SMTP conversation inside the request.
- **`GET /utils/health-check/`** (`utils.py:29-31`) is trivial; it should stay fast and is the right smoke target — but it too returned status `"0"` here.
